# Windows / WSL 统一校时与回拨排查

日期：2026-09-05，Asia/Shanghai。
最新结论：**统一校时并按用户授权重启 WSL/Docker 后，120 秒真实时钟采样无回拨，默认时钟短时联调通过。**
没有改动 NoMaD 控制器或放宽保护。下文首先保留重启前的诊断及失败记录，重启后结果见末节。

## 证据与判断

此前两次控制器日志记录的系统时间回拨分别为 3.701850983 秒、3.670478502 秒，
同时单调计时器分别前进约 54.97、54.93 毫秒。

修改前检查：

- Windows `W32Time`：Stopped / Manual；已配置 `time.windows.com,0x9`，非域成员。
- Windows 对原 NTP 服务器的三次只读偏差采样约 −3.715 至 −3.780 秒。
- Ubuntu-22.04 `systemd-timesyncd`：active / enabled，来源 `ntp.ubuntu.com`，报告偏差 −3.804445 秒。
- Hyper-V 隐式时间同步：`hv_utils.timesync_implicit=Y`。
- WSL 2.6.1.0，内核 6.6.87.2-microsoft-standard-WSL2，当前 clocksource 为 `tsc`。
- Ubuntu timesyncd 日志查询未返回条目；不能据此还原每一次校时操作。

两套校时机制冲突是有证据支持的风险；但停用独立 NTP 后仍发生回拨，
因此不能将它视为全部根因，也不能声称统一来源已修复 WSL 底层计时。

## 已实施的最小修改

目标同步路径：`time.windows.com → Windows W32Time → Hyper-V/WSL → Docker 容器`。

1. `systemctl disable --now systemd-timesyncd.service`：仅在 Ubuntu-22.04 执行。
2. Windows `W32Time` 改为 Automatic 并启动。
3. 保持已有 NTP 服务器及 `0x9` 标志不变，执行 `w32tm /resync /rediscover`。
4. 初次大偏差纠正后服务仍报告未同步，随后再次请求同步并确认成功。

最终 Windows 状态：Leap Indicator 0、Stratum 5、来源 `time.windows.com,0x9`、
最后同步错误 0、最近成功同步时间 18:10:03。服务报告相位偏差约 +0.074 秒。
初次纠正由 Windows Kernel-General 事件记录为 −3862 ms；这是本次授权校时产生的一次调整。

Windows 校时修改使用管理员 UAC 授权。实现脚本为
[unify_host_time.ps1](../docker/ros2/unify_host_time.ps1)，不会自行修改服务器、重启容器或更换内核时钟源。
脚本成功退出仅表示配置及 resync 请求成功，不代表时钟稳定性验收通过。

## 重启前复验结果：未通过

1. 使用默认真实 ROS 时间、没有 `/clock` 发布器，连续采样约 120 秒、5840 组：
   **仍有 4 次回拨**，ROS 步进相对单调时间的最大偏差约 **1150.14 ms**。
2. 默认时钟真实视频/CUDA NoMaD 联调通过了前 14 项检查，包括真实推理到预览输出、
   推理进程退出后归零；在最终控制器退出测试准备阶段遇到 `clock_rollback`，整次验收失败。
3. Windows 与 Ubuntu/容器的配对采样中，估计 Linux 领先约 0.508–0.674 秒；
   每次命令时延造成的误差界约 ±0.060–0.117 秒，不能当作精密授时测量。
4. 单次管道计时对比：Linux 单调时间经过 10.0116 秒，Windows Stopwatch 经过 9.6065 秒。
   存在程序/管道计时误差，此项仅作为走时速率异常的线索，不能单凭它认定 TSC 硬件故障或精确漂移率。

## 回退说明

原始配置已保留。如用户明确要求恢复原状态：在管理员 PowerShell 将 `W32Time` 停止并设回 Manual，
再在 Ubuntu 执行 `systemctl enable --now systemd-timesyncd.service`。
这会重新引入双重校时风险，不建议作为正常方案；恢复服务配置不会把系统时钟拨回旧时间。

## 用户授权重启后的结果（同日 18:28 更新）

1. 保存原 5 个运行容器的 ID 和启动信息，停止容器。
2. Docker Desktop 常规退出 45 秒超时；随后使用官方 `docker desktop stop --force` 退出，

3. Docker CLI 一度误报 Desktop 已运行，而进程和引擎不存在；直接启动已核实路径的
   Docker Desktop 程序后，引擎 28.5.1 就绪。
4. 按原始 ID 恢复全部 5 个容器，未删除、重建容器或镜像。原先手动执行的容器内任务并不自动恢复。
5. 两个项目容器仍显示 `Asia/Shanghai`，GPU 可见；Windows 时间服务 Running/Automatic，
   同步状态成功；Ubuntu 独立 NTP 仍 inactive/disabled，Hyper-V 隐式同步仍为 Y。

复验：

- 120 秒默认真实 ROS 时钟：5886 组采样，**0 次回拨**；控制器两份源码哈希与修改前一致。

  这一方向，但不据此认定精确内核根因或保证未来不再回拨。
